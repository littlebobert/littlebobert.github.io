KN001: Foundation Models in the Background

Karui

Understand how Apple’s on-device Foundation Models limit apps running in the background, and how Karui copes.

September 28, 2026 · iOS 27.0 · Measured on iPhone 17 Pro

Overview

Karui is an on-device iPhone notification filter built on iOS 27’s new notification trigger.

iOS 27’s “When I receive a notification” Shortcuts trigger runs an automation for each notification from the apps you choose. Karui’s automation calls an App Intent that doesn’t open the app. The intent builds a prompt and makes one non-streaming, guided-generation request with LanguageModelSession:

let decision = try await session.respond(
    to: prompt,
    generating: TriageDecision.self
)

With Karui on screen this takes about 4 seconds, but in the background the request is often refused.

Apple documents that the limit applies only in the background, but not how large it is or how it recovers. These measurements come from one iPhone’s logs over a few days, and Apple may change the behavior.

Apple’s TN3193 covers the model’s context window. This note covers how often an app can use the model in the background.

What the limit looks like

Refusals arrive as the rateLimited generation error within 13 to 34 milliseconds, too fast for the model to have run, so the request is refused before it starts. Apple’s documentation for the error says:

“This error will only happen if your app is running in the background and exceeds the system defined rate limit.”

In Karui’s logs the pattern was consistent: a burst of accepted calls, then hours of refusals.

All calls in the background, with the iPhone unplugged. Three slow calls of 8 to 15 seconds got through after midnight on the first night.

In one case, refusals continued across a 74-minute gap with no calls at all, so this doesn’t look like a simple hourly quota that refills while you wait.

Factors that did and didn’t affect refusals

Karui logs the device’s state with every model call. Refusals happened with the iPhone locked and unlocked, at nominal thermal state, with Low Power Mode off, and at 60 to 100 percent battery.

As Apple’s documentation says, calls with Karui on screen weren’t affected: at 20:37 one succeeded while background calls at 20:30 and 20:41 were refused.

One night on the charger, all 10 background calls between 01:30 and 05:51 succeeded, so charging might matter. They were also spread out, about two an hour, so it’s unclear whether charging or the spacing made the difference. The first refusal came 15 minutes after the iPhone was unplugged.

Misleading symptoms

The error message

The rate-limit error suggests using non-streaming requests in background activities. Karui never streams, so that advice doesn’t apply.

Timeouts that are really suspensions

One call “timed out” after 70 seconds against a 20-second limit. ContinuousClock keeps counting while the process is suspended, and iOS had suspended Karui mid-call. When a background model call takes far longer than your timeout, suspect suspension before blaming the model.

Other failures

Rarely, a call fails with an error from the safety layer’s sensitive content analysis instead. Karui treats it like any other failure.

Coping

Karui still delivers every notification when the model refuses:

  1. It falls back to rules. A deterministic classifier decides right away. Important contacts, mentions, one-time codes, and urgent terms were already decided by rules before the model ran.
  2. It rechecks in the foreground. Notifications decided by rules because of a rate limit are marked and reclassified the next time Karui is opened.
  3. It tries BGProcessingTask. Karui schedules one after a rate limit, and iOS ran them 15 minutes to 2 hours later, even unplugged. Whether model calls from a background task get a larger budget is still unknown: by the time they ran, there was nothing left to recheck.

Asking Private Cloud Compute instead

Karui doesn’t call Private Cloud Compute itself. The user’s shortcut does, with the Use Model action:

  1. The triage intent returns its result, a flag asking for a second opinion, and a ready-made prompt.
  2. If the flag is set, the shortcut runs Use Model with Private Cloud Compute and that prompt.
  3. The shortcut passes the answer to a second intent, which updates the classification and alerts the user if the answer is Important.

In the logs, all 8 rate-limited notifications one morning got a cloud answer 2 to 3 seconds after the on-device refusal. One was Important and was delivered, when the rules alone would have filed it as Neutral.

Because the round trip is fast, Karui offers three modes:

  • When Needed asks only after an on-device failure.
  • Always asks after every on-device answer, alerting right away and correcting afterward.
  • First, which is experimental, holds an on-device Important for up to 20 seconds while the cloud answers. The held alert is a scheduled local notification that iOS delivers even if the cloud never answers, so the alert still arrives if the shortcut fails partway.

The prompt sent to the cloud contains only the notification’s text and app, the user’s names, and their sorting terms. Anything the rules decide never leaves the iPhone.
