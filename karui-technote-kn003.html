KN003: Getting Reliable Answers from the On-Device Apple Foundation Model

Karui

Prompt and schema choices that made Apple’s on-device model categorize Karui’s notifications more reliably, and where hard-coded deterministic rules do better than the model.

September 28, 2026 · iOS 27.0 · Tested on iPhone 17 Pro

Overview

Karui is an on-device iPhone notification filter built on iOS 27’s new notification trigger. For each notification, Apple’s on-device model decides whether it’s Important, Neutral, or Spam, with a short reason. Each change below fixed a specific wrong answer seen in my Karui History.

There is some overlap with Apple’s TN3193 here, which covers keeping your prompts small.

Put the reason before the answer

A Generable type’s properties are generated in the order they’re declared. With the category first, the model picked a category and then wrote a reason to justify it. With the reason first, the category follows from what the model just wrote:

@Generable
struct TriageDecision {
    @Guide(description: "What the notification is and what, if anything, it asks of the user and by when")
    let reason: String

    @Guide(description: "The notification handling decision that follows from the reason")
    let category: TriageCategory
}

The reason’s guide also tells the model what to look for: what the notification asks of the user, and by when.

Name and order the options on purpose

Neutral comes first: an unsure model tends to take the first option, and it had been taking an urgent-sounding one.

@Generable
enum TriageCategory {
    case neutral
    case important
    case spam
}

Give the model what it can’t know

The model has no clock, so without the time a notification arrived, “tomorrow” in any message read as urgent. Each prompt now starts with it.

Received: Monday, September 28, 2026 at 12:59
Source: Slack
Source is an important app: no
Sender: Kensuke Sada
Title: Reply from Kensuke Sada
Subtitle (often a chat or thread name): #internal-kotoba-app-sales
Body: @Yuta SASAKI When does this look like it will happen?
Addressed to: @Yuta, not the user

Only say what’s true

Most apps never mark notifications time sensitive, and the model read “Time sensitive: false” as “not urgent.” The prompt now mentions it only when it’s true. Similarly, an empty list of terms read as a dangling label, so an empty field now says “none.”

State facts instead of hoping for inferences

The model treated “@Yuta, can you send me that report?” in a Slack channel as a request to the user. Karui now finds the @names in a message, and if none is the user, adds a line saying so, as in the example above. The instructions also name the case: a message addressed to someone else is Neutral.

The same applies to what the model shouldn’t guess. It linked messages to the user’s calendar events that had nothing to do with them, so the instructions now say to connect a notification to an event only when it names that event or matches its place or time.

Check the answer with rules

Even with “Addressed to: @Yuta, not the user” in the prompt, the model kept marking that Slack message Important. So after the model answers, a rule checks it: if the model says Important but the message is addressed only to other people, the result drops to Neutral with the reason “Addressed to @Yuta, not you,” unless the message matches the user’s urgent terms or is marked time sensitive. For reference, Private Cloud Compute got the same message right without the check.

Decide with rules first where the answer is certain

Messages from the user’s important contacts, mentions of the user, one-time codes, and matches for the user’s urgent terms never reach the model. Rules decide them instantly and can’t get them wrong, and every call they save is one more in the small background budget that KN001 describes.
