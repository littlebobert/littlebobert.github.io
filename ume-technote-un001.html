UN001: Testing Form Matching on 184 Forms I’ll Never Fill Out

Umete

How I test Umete’s form matching without filling out forms myself, the bugs the test caught, and how much AI matching adds.

November 19, 2026 · Umete 0.4.9 · 184 forms from Chromium’s autofill tests

Overview

Umete automatically fills complete web forms with answers saved from previous forms. Matching happens on your device first, from each field’s label, name, placeholder, and autocomplete hint. Fields it can’t place can go to an AI, which sees only descriptions of the fields, never your answers.

I don’t fill out many forms, so I don’t get to try Umete as often as my other apps. This note covers a test that replays real forms instead, what it found, and what AI matching adds on top of local matching.

The test

Chromium keeps a set of saved forms for testing its own autofill: checkout and sign-up pages from sites like Lowe’s, Macy’s, and Walmart, plus forms in 13 other languages, each with the type Chromium expects for every field. The test runs Umete’s real extension scripts on all 184 of them:

  1. A fictional person in San Francisco fills one sign-up form and chooses Remember my answers.
  2. Each saved form opens in WebKit, the engine behind Safari, with the page’s own scripts and all network access off, and Umete runs Fill this form.
  3. Every field Chromium labeled is checked: filled correctly, filled wrongly, or missed. A field the person has no answer for, like a middle name, should stay empty. Card numbers and passwords must never be filled, and none were.

A wrong value is worse than an empty field, since you might not notice it. So I look at two numbers: precision, how many of Umete’s fills were right, and recall, how many of the fields the person had an answer for got one.

Update: Umete 0.5.2 and Firefox’s forms

November 25, 2026. The test now also runs 36 forms from Firefox’s autofill tests, checkout and sign-in pages from Best Buy, Costco, Home Depot, Walmart, and others. Firefox’s tests list the fields Firefox finds without saying which element each is, so I lined them up with each page and checked every one by hand, correcting the fields Firefox gets wrong, like an address nickname it calls a street line.

The two sets found more wrong fills, all fixed in Umete 0.5.2: a ZIP code in coupon, captcha, and ZIP+4 boxes, the whole phone number in an Area Code box, the apartment in two fields, and a City field read as ZIP because of the error message inside its label. The biggest change was reading labels on older pages that put a field’s name in the cell beside it instead of in a label, which most of the recall gain in the table above comes from. On both sets together, 1,123 of Umete 0.5.2’s 1,124 local fills were right (99.9%), with 66.5% recall and no password or card number filled. The one wrong fill is a phone field Chromium expects only the area code in. With AI matching as well, recall on both sets rose to 85% at 99.0% precision (1,439 right, 14 wrong). Of the AI’s 13 wrong fills, four are arguably right (a “first surname” in Spanish forms got the person’s one surname, and a Turkish “city” field Chromium expects a state in got the city), six put the whole street line in a box for the street name alone, and three are plain mistakes, such as a street address in a First Name field. The details below are from the first run, on 0.4.9.

What the test caught

The first run found bugs I hadn’t run into myself, all fixed in Umete 0.4.9:

  • A field labeled just “Address” incorrectly got your email address. This was the biggest source of wrong fills.
  • Address line 2 got your street, when the form you remembered had no second line to match it.
  • A phone number split into boxes for area code, prefix, and line number went whole into the first box. Umete now fills each box with its part, and leaves alone a box too short for the number.
  • When a dropdown sat inside its label, Umete remembered the label with every option in it, like “State Select a state Arizona California…”, which made the answer hard to match later.
  • A lone “Area code” box got the ZIP code. ZIP+4 and phone extension boxes got answers too; they now stay empty.

Each fix was checked against the whole set. No field that 0.4.8 filled correctly is missed by 0.4.9. Five fields that 0.4.8 left empty now get a wrong value, mostly on pages where the label Umete reads doesn’t say what the field is.

What AI matching adds

After local matching, Umete asks the AI about the fields it left unhandled, one multiple-choice question per field: which saved answer belongs here, or none. It fills a field only when the AI is at least 60% sure. The test used OpenAI’s Decisions API with gpt-6-luna, the setup Umete uses by default.

  • Of the 746 fields local matching missed, Umete asked the AI about 652. Most of the rest it leaves empty on purpose, like a second phone number on the same page.
  • 465 of those now got the right answer, and 14 a wrong one. The AI’s biggest help was with labels local matching can’t read: table layouts with the label in another cell, and forms in German, Korean, Russian, and other languages.
  • Some of the 14 are arguable. A Spanish form’s “Primer apellido”, the first of two surnames, got the person’s only surname, and street name fields got the whole street line.

AI matching added less when the person’s address was saved in the app as a structured address instead: recall went from 48.3% to 66.6%. Umete fills structured addresses only locally and never sends address fields to the AI, so their misses stay. That’s the next thing to work on.

Limits

  • Chromium’s labels are its own predictions, kept to catch changes in its autofill, not answers someone checked by hand. A few are debatable, such as a gift recipient’s email labeled as the person’s.
  • The pages are old saved copies that run no scripts, so the test doesn’t cover custom dropdowns, fields inside web components, or forms built as you go. I try to check those on live sites.
  • It’s one fictional person with a US address, and the AI results are from a single run. AI answers can differ a little from run to run.

The test is open source with the rest of Umete, in github.com/littlebobert/umete/eval.
